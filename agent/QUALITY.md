# 判断质量检查

质量检查分成两个层面：

- 机械检查：字段、引文存在性、支持关系和结论的组合、汇总一致性。
- 指定语义断言：给定JD与事实后，明确要求应得到什么结论、类别或关键证据引用。

## 冻结的成对基准

src/jobmatch/resources/benchmarks/quality-pairs-v1.json包含5组、10例合成案例，随wheel一同分发：

| 改变的条件 | 观察点 |
|---|---|
| 硕士门槛→博士门槛 | 结论应随明确学历差异改变 |
| Python或Java→Python且Java | 不把“或”变成全部必须，也不遗漏“且”的缺口 |
| 课程接触→直接部署/排障实践 | 判断应随证据强度改变 |
| 必需经验→加分经验 | 缺少加分项不应否定已满足的核心要求 |
| 普通JD→加入不可信指令 | 数据中的命令不应改变结论或被当作候选人要求 |

预期在运行前保存；案例ID、预期、理由和可能暗示答案的来源文件名不进入模型请求。送入模型的证据来源使用中性标识，原出处保留在本地案例文件。

这些案例由助手编写，provenance=synthetic，不是独立人工能力金标。旧50岗兴趣标注继续单独报告，不替换为这套断言。

## 运行与比较

    uv run jobmatch semantic-check --suite quality --provider cpa
    uv run jobmatch semantic-compare --before "<第一次目录>" --after "<第二次目录>"

同一评测集和预期才能比较。改了断言、漏跑案例或结果重复时拒绝直接比成绩；比较会列出代码、模型、配置和运行环境等变化，多个因素同时变化不能归因于某一项。

报告保留：

- 案例和断言通过数量；
- 成对条件变化是否符合预期；
- 漏提取、误判满足、误判不满足、类别/支持错误、关键引用缺失；
- 尚未被断言覆盖的要求数量；
- 每例原始JD、候选事实、匹配结果、错误及来源类别。

基准通过仅说明这些断言通过，population_accuracy保持null。判断改进需要同集对照及人工语义复核，不能用机械通过率代替。

## 中断

semantic-check使用与其他批次相同的检查点，可用resume继续。失败和旧报告保留，已完成的案例不重新调用模型。详见 RECOVERY.md。
