# End-to-end workflow

## 1. 建立上下文

读取当前候选人的本地档案、选岗规则和投递主表快照。个人事实、偏好、经历边界和当前状态必须分开处理：

- 事实：来自候选人档案或明确凭据；
- 偏好：来自当前选岗规则；
- 状态：来自主表和官方账号/邮件证据；
- 推断：只能作为待核项，不能写成事实。

不要把上一次会话记忆、浏览器自动填充值或 AI 推断当作档案来源。

## 2. 公司研究与岗位选择

1. 查重已有公司、岗位和额度记录。
2. 定位官方校招入口，区分校招、社招、实习和不同招聘主体。
3. 获取完整岗位目录，保存原始快照；不要用首页第一屏或关键词结果冒充全量。
4. 逐个阅读范围内岗位的完整 JD，记录至少两条原文引文、硬门槛、匹配点和缺口。
5. 按 schema v2 保存 `raw_catalog` 的显式 ID 提取规则和 `coverage` 状态；每个范围内岗位保存共享 JD/候选人来源，并用 `requirements[]` 做逐项映射。
6. 运行 `verify-matching.py`，按 `checks`、`positions[]` 和 `readiness` 判断是否可以生成比较记录或登记新岗位；登记前把用户选择的 `selected_position_id` 传入，并核对它位于 `registerable_position_ids`，不要只看全局布尔值或 `passed`。
7. pipeline 验证后生成 human-summary.json；向用户展示岗位比较时必须包含 **S/A/B/C + 证据匹配度区间（非录用率）+ decision + 是否可登记 + 关键缺口**，不能只给机器状态。
8. 将首选和替代岗位交给用户确认；有限志愿、顺序、投后修改限制和截止日必须显著呈现。

## 3. 登记本地投递主表

选定岗位且 matching 报告具备登记条件后按主表适配器执行：

```text
snapshot → plan → preview → apply → snapshot/read-back → validate
```

新岗位只登记为 `Pending`/等价的待投状态。计划投递日期不能冒充实际提交日期；岗位 ID 是稳定关联键，不以公司名或行号定位。

## 4. 准备网申材料

读取具体 JD 和候选人档案，选择与岗位真正相关且已证实的经历，确定 A/C 或其他简历版本。为本次申请建立私有材料快照，记录：

- 官方 JD URL、读取时间和完整正文；
- 实际使用的简历版本及文件校验值；
- 自定义问答原文；
- 选用经历、理由与表述边界。

材料快照放在被 `.gitignore` 排除的私有目录，绝不放进公共 Skill 仓库。

## 5. 填写网申

识别 ATS 家族后复用家族知识，再探索公司特有字段。上传、解析或自动复用后必须检查：

- 文本输入值；
- 原生 select 与自定义 combobox 的实际选中项；
- 日期粒度和教育/实习/项目顺序；
- checkbox/radio 状态；
- 所上传的简历文件名；
- 解析残留和字段错位；
- 对共享简历/profile、自动复用字段和高影响结构化字段，在站点提供可靠同源读取能力时做保存后的服务器/独立只读页核验，避免把“当前 UI 正确”误当成“服务器真值正确”。
- 共享最新资料与单次申请快照要分开：拿不到历史申请快照时，不用当前共享资料反推历史投递的精确字段。

浏览器执行通道与提交授权分开处理：优先使用当前运行时可靠的浏览器；需要本地专用浏览器时，可用 Playwright + 非默认持久化 profile 执行上传、解析纠错、填写和读回。Raw CDP 不作为普通 ATS 填表首选。提交模式默认为 `review`（停在最终提交前）；用户可对明确岗位/批次设置 `preauthorized`，或另外明确限定 `autonomous` 范围。无论模式如何，验证码、未知高影响问题、额度/志愿冲突和不可逆不确定项都必须人工接管。

## 6. 提交与凭据

只有当前授权模式允许最终提交，并且全表审计无未决错误时，才可执行最终外部副作用。**表单完整不代表项目提交门完整**：提交前还要核项目总额度、同单位额度、志愿/aspiration 顺序、投后修改/撤销限制等项目级状态。提交请求即使 HTTP 200，也必须检查业务 code/msg。若返回“志愿不完整/顺序缺失/项目设置冲突”等业务失败，先查询账号投递记录确认没有实际生成申请，再通过官方项目配置、实际弹窗或只读前端行为定位缺失门；涉及稀缺志愿、不可修改顺序或其他岗位影响时重新交给用户确认。补齐后只做有界重试，并在重试后再次读取官方投递记录。只有真实成功页面、稳定 application ID/账号记录、确认邮件或用户明确确认，才能把申请改为 `Submitted`；在同一事务中追加申请日志，保存凭据和材料快照引用。“按钮点击完成”或“HTTP 200”本身都不是证据。

## 7. 同步在线进度视图

本地变更完成并读回后：

1. 从 `sync_queue` 导出本批 payload；
2. 先执行 `dryRun=true`，查看重复记录、归属冲突和字段差异；
3. 确认无错误后执行写入；
4. 每条写入后读回详情和阶段；
5. 通过 `change_id`/revision 做 `sync-ack`；
6. 再次读取本地队列，报告成功与剩余 pending/error。

管理区以稳定岗位 ID 和内容校验值定位。管理区外的人工备注逐字保留；发现人工改动或同名候选冲突时停止该条，不强行覆盖。

## 8. 收尾

最终报告区分：研究完成、已登记待投、已提交、线上已同步、待用户操作、待核实和失败保留项。不能用预览成功、导出成功或启动浏览器来代替线上成功凭据。
